# Branch Lens

Read-only branch briefing at `/#brief`. Uses the existing authenticated Growth endpoint and shared ratings reader; no AI service, new route, database change, collector dispatch, credentials or additional paid dependency.

Brand logo cards replace text lookup. Cards follow the approved brand priority, and expanding a brand reveals only its branches from the current authorized saved-comparison catalog. Selecting an exact branch opens its report immediately. Escape and the close control collapse the branch list; the report remains labeled with its selected brand and branch while another brand is being browsed. Every server-filtered source ID is retained. Canonical display aliases group cross-platform results, while multiple rows for the same platform make that platform ambiguous and suppress its conclusion.

Each platform keeps its original date pair, metric basis, completeness exclusions and recommendation. Client movement is recomputed from finite current/previous sales; missing and zero are distinct. A zero previous baseline has no percent-change claim. Small samples and low confidence remain explicit. No cross-platform sales/profit total or composite score is invented. Each recommendation is a next check, not a proven cause; English source evidence/unknowns and the existing exact-branch detail drawer remain accessible. Persian recommendation copy is a fixed translation of the existing rule codes. Unknown rule codes do not generate invented advice.

Current ratings are separate dated snapshots matched on canonical brand/location, with individual platform health and source status. They are not time-aligned to weekly sales or averaged. Reviews, Deliveroo operational reports and profit are not assessed in this view. Missing platforms are not evidence of healthy performance. The overview uses 3 supported sales platforms as the coverage universe; absent/ineligible comparisons count as unavailable.

Language switch preserves the selected branch. Background renders do not interrupt an expanded branch picker or focused selection controls, and auth reset clears state and invalidates pending work. Uses shared auth-generation protections and scoped server readers. No sensitive branch context is written to browser storage or URLs.

Validation: pure core checks cover Persian/English lookup, ambiguity and authorized-scope boundaries, same-platform collisions, null/zero/failed/stale comparisons, zero baseline, independent arithmetic, source identities and exact ratings match. Local synthetic browser checks cover Persian result, English switch, evidence drawer, light/dark and 390px layout. Full suite and deployed checks are recorded in checkpoint64. Synthetic results are not production evidence.

## Detailed field reports

Growth now carries a narrow `diagnostics` projection for each already-scoped branch and matched period. There are no additional database round trips or collectors. Talabat projects daily metrics from the existing 14-day history read: stage counts require seven unique present days; preparation is weighted by successful orders; avoidable waiting is total minutes divided by successful orders, never a daily total mislabeled as an average. Missing daily metrics remain unknown. Keeta takes service values and customer-stage counts from the authorized shop/customer report; historical service values are unknown when no exact prior shop snapshot was required or available. Customer-stage counts are not valid-order counts. Noon requires the nested dashboard's four dates to match the sales comparison; zero-order preparation/wait averages are unavailable. Its absent prior funnel stays unknown.

`branch-story.js` separates measured issues from hypotheses. Current/prior views falling with orders is an observed association; preparation or offline-time explanations are explicitly unproven hypotheses. They require a valid exact-period comparison and at least20orders in both periods. Preparation must have worsened by more than0.5minute, or exceed the user-approved14minute preparation review threshold on any platform. Offline review uses an internal2% screen. These are investigation cues, not official platform SLAs. Rising sales never produce an explanation of lost orders. Excluded or duplicate source comparisons never generate a diagnosis.

The revised platform field report has exact current/previous sales, signed AED/% movement, orders and basket, independent stage bars, available-service metrics and issue bullets, then a separate next-check/hypothesis strip. Stage ratios are descriptive and never presented as a traced customer cohort. Each field report retains dates, source evidence, confidence and the original exact-source detail control. Persian page headings/forms/results use RTL; numbers, dates and rating snapshots retain readable direction.


## Selection and visual hierarchy refresh
Logo assets reuse the optimized WebP files. The brand rail stays on one row with local scrolling on narrow screens; its expandable branch panel is outside the scrolling rail. No text input, submit step or example query remains. Bilingual direction, focus restoration, auth reset and exact-source detail navigation remain. Platform sections have larger distinct headings, clearer status labels, stronger sales movement, and labeled current/prior proportional sales bars. The sales bars use the same validated values as the existing text; zero baselines and unavailable comparisons retain their existing rules.


The branch directory is the union of independently authorized Growth and ratings identities. Missing sales-source reads cannot erase rating-directory brands. All three supported sales platforms retain an explicit report slot with unavailable reason when no row was received. Placeholders contain null metrics and no fabricated source identity; diagnosis/evidence navigation remain disabled. A partial-load notice exposes failed platforms and a retry control. If the Growth request fails entirely but scoped ratings succeed, the directory still works with unavailable comparisons. This does not repair upstream read failures or fabricate sales.


Low latest ratings (existing WARNING/CRITICAL source status) are repeated in the same platform’s issues panel with exact rating, timestamp and source health. They remain explicitly independent of weekly sales and do not establish a cause. Rating issues can appear even when the sales comparison or operational metrics are unavailable; other platforms’ ratings never leak into that panel. Summary issue counts include only signals rendered in supported platform panels.
