## ۲. گواهی اتصال دیتابیس

روی production به‌صورت فقط‌خواندنی و سپس روی شاخهٔ بازیابی، با همان درایور pg سه حالت آزمایش شد:

| حالت | نتیجه |
|---|---|
| زنجیرهٔ معتبر و نام سرور درست، rejectUnauthorized=true | موفق؛ TLSv1.3 / TLS_AES_256_GCM_SHA384 / authorized=true |
| CA نامعتبر/خالی | رد شد؛ UNABLE_TO_GET_ISSUER_CERT_LOCALLY |
| بررسی نام سرور اشتباه | رد شد؛ ERR_TLS_CERT_ALTNAME_INVALID |

پس از این اثبات، `database-config.ts` برای داشبورد اضافه شد: اعتبارسنجی گواهی برای میزبان غیرمحلی اجباری است؛ گزینه‌های SSL داخل DSN نمی‌توانند آن را خاموش کنند. فقط hostname دقیق localhost/127.0.0.1/::1 مسیر محلی بدون TLS دارد؛ وجود کلمهٔ localhost در نام کاربری/رمز یا مسیر دیگر اثری ندارد. این تنظیم از CAهای عمومی Node استفاده می‌کند؛ اگر در آینده mTLS یا CA اختصاصی لازم شد باید پشتیبانی صریح اضافه شود، نه گزینهٔ no-verify.

تست پیکربندی، هر دو ساخت TypeScript و تمام۲۳۴تست داشبورد پاس شدند. commit6a51d18؛ آزمون شاخه39233193395 و main39233443863 موفق‌اند؛ انتشار production درVercel21zLUAzav3np8NJijX8wspAKFwZu موفق شد. بررسی فقط‌خواندنیِ سایت پس از انتشار در خروجی همراه ثبت می‌شود. هیچ رمز یا حساب واقعی reset نشد.

## ۳. بار هم‌زمان با دادهٔ واقعی

روش: GitHub runner، یک پردازهٔ Node و HTTP محلی، handlerهای واقعیِ commitbd6bcff داشبورد، احراز هویت واقعی و SQL واقعی روی شاخهٔ بازیابی؛ proxy upstream روی HTTP loopback و با readerهای واقعی دادهٔ همان شاخه. دو pool برنامه هرکدامmax3 و یک اتصال کنترل؛ نمونه‌برداری از تعداد اتصال/صف هر۱ثانیه. فقط یک نشست آزمون در شاخهٔ آزمایشی ساخته و در پایان پاک شد. هیچ ترافیک بار به سایت یا دیتابیس اصلی فرستاده نشد.

مسیرها: ratings چهار پلتفرم، فروش هفت‌روزه، ریویوها، Keeta، Noon و تاریخچهٔ یک شعبه. تمام warmupها دادهٔ واقعیِ غیرEMPTY دادند. کاربران مجازی در اجرای نهایی هرکدام۲درخواست متوالی با۵۰۰میلی‌ثانیه مکث داشتند؛ این تستِ burst کوتاه است، نه آزمون پایداری چندساعته.

مشاهدات: حداکثر۷اتصال دیتابیس؛ صف pool داشبورد تا۵۵ و upstream تا۳۹؛ RSS پردازه تا۳۶۲MiB؛ CPU پردازه در مرحله۵۰کاربر۱۰٫۸درصد یک هسته؛ p95وقفهٔ event loop حدود۲۲ms با resolution20ms. CPU و RAM مربوط به پردازهٔ runner هستند، نه مصرف Neon یا دستگاه کاربران. تعداد connection شامل اتصال کنترل نیز هست.

اولین اجرا39232952624 هرکاربر۳درخواست داشت؛۱۰کاربر۰خطا،۵۰کاربر۱۱خطا گزارش کرد که۴مورد آن رسیدن به سقف۶۴MiB ابزار بود. برای رفع این عامل مخدوش‌کننده اجرای نهایی کوتاه‌تر شد و پاسخ ناقص۲۰۰نیز خطا حساب شد. اجرای نهایی۴۲٫۰۸MiB پاسخ و صفر خطای بودجه داشت؛ آن۲۱مورد خطا/نقص را نباید به سقف ابزار نسبت داد.

**تفسیر:** صف انتظار و خواندن‌های تکراری زیر بار بالا بهبود می‌خواهند. برخی historyها هنگام نقص منبع به۴۰۳می‌رسند؛ این fail-closed است و دسترسی اضافی نمی‌دهد، اما پیام مناسبی برای خطای زیرساخت نیست. این رفتار و سرعت پاسخ زیر۵۰کاربر اکنون تأیید مطلوب ندارند. اولین اقدام مناسب کاهش خواندن‌های تکراری هم‌زمان با حفظ محدودسازی مستقل هر کاربر، کاهش هزینهٔ gate تاریخچه و سپس بازآزمایی است؛ زیادکردن کورکورانهٔ تعداد اتصال راه‌حل تأییدشده نیست.

**مرز نتیجه:** این آزمون مرورگر/رندر، CDN، شبکهٔ کاربران، cold start یا تکثیر نمونه‌های Vercel را نمی‌سنجد. هنوز نمی‌گوییم سایت زنده۵۰کاربر را با همین درصد خطا پاسخ می‌دهد یا عدد ظرفیت نهایی آن همین است. عملکرد انیمیشن‌های صفحه نیز در این آزمون موضوع سنجش نبود.
